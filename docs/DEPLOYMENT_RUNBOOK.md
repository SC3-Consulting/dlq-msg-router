# Infrastructure Deployment Runbook: Autonomous DLQ Agent

This document outlines the step-by-step procedures for provisioning the secure, Zero Trust infrastructure for the Autonomous DLQ Triage Pipeline via Terraform. It serves as a comprehensive, zero-assumption guide designed to take an operator from a blank terminal to a fully operational, AI-augmented triage agent in Azure. 

Every command, operational trap, and environmental patch required for a flawless execution is documented below.

---

## Architectural Context & Permission Constraints

To adhere to strict enterprise security mandates, the deployment is orchestrated via PowerShell wrappers. This ensures secure injection of CLI credentials without exposing sensitive variables to version control. 

**The Resource Group Strategy:** Initially, separating the remote state storage (Storage Account and Key Vault) into a dedicated resource group is best practice. However, due to tenant-level 'User Access Administrator' restrictions preventing cross-resource-group role assignments, all infrastructure—including the state bootstrap—must be encapsulated within a pre-existing resource group (e.g., 'rg-viva-dlq-dev') where 'Owner' permissions are already established.

## Phase 0: Pre-flight Preparation & Code Patching

Before initiating the deployment, authenticate your terminal, generate your keys, and patch the agent to bypass ephemeral storage limitations.

### 1. The Ephemeral Storage Patch
Azure Container Apps utilise ephemeral disks. Attempting to extract physical CSV telemetry files via the Azure CLI requires deep RBAC container execution permissions, triggering an 'AuthorizationFailed' error. 

To bypass this securely, modify your local 'src/run_agent.py' file. Inside the 'log_telemetry' method, locate the 'row' array declaration and inject this exact print statement immediately after it to broadcast the telemetry directly to Azure Log Analytics:

    print(f"CSV_EXPORT|{','.join(map(str, row))}")

### 2. Authentication & Key Generation
Authenticate with Azure:

    az login

Generate a local SSH key pair to securely access the Azure Bastion Jumpbox. Do not set a passphrase when prompted:

    ssh-keygen -m PEM -t rsa -b 4096 -f ~/.ssh/viva_jumpbox_rsa -N ""

## Phase 1: Remote State Bootstrap

**Objective:** Provision the foundational Azure resources required to securely execute Terraform. This creates the Storage Account for the '.tfstate' file and the Key Vault.

1. Execute the Phase 1 PowerShell orchestrator from your local repository root:

```bash
pwsh ./infra/scripts/01-bootstrap.ps1
```

2. **Trap Resolution (Soft-Deleted Vaults):** If a previous deployment failed or was torn down, Azure retains Key Vaults in a soft-deleted state, which will block recreation. If the script fails due to a name conflict, purge the old vault manually. Replace 'YOUR_VAULT_NAME' with the output generated by the script (e.g., 'kvtfstatelogia7'):

```bash
az keyvault purge --name YOUR_VAULT_NAME --location australiaeast
```

3. **Secure Key Injection:** Once the Key Vault is provisioned, you must manually read your generated public key and inject it into the vault as a secret. Execute these commands in PowerShell:

```bash
$PubKey = Get-Content ~/.ssh/viva_jumpbox_rsa.pub -Raw
az keyvault secret set --vault-name YOUR_VAULT_NAME --name jumpbox-admin-ssh-public-key-dev --value "$PubKey"
```

4. Initialise the Terraform backend memory to link your local workspace to the newly created Storage Account:

```bash
    terraform -chdir=infra/terraform/azure init -reconfigure -backend-config=environments/dev/backend.hcl
```

## Phase 3: Jumpbox Provisioning & The Split-Brain Fix

**Objective:** Securely breach the private network via Azure Bastion, configure the bare-metal Jumpbox, inject the environment variables, and push the Docker image.

### 1. Synchronise Code
Push your latest local code to your repository so it can be cloned inside the isolated Jumpbox:

```bash
    git add .
    git commit -m "Syncing code for Jumpbox deployment"
    git push
```

### 2. Breach the Jumpbox
1. Navigate to the Azure Portal.
2. Open 'vm-jumpbox-dev' and select 'Connect' -> 'Bastion'.
3. Username: 'azureuser'
4. Authentication Type: 'SSH Private Key from Local File'.
5. Upload your private key ('~/.ssh/viva_jumpbox_rsa' - select the file WITHOUT the '.pub' extension).
6. Uncheck 'Open in new browser tab' to avoid popup blockers, then click 'Connect'.

### 3. Provision the Bare-Metal Environment
The Jumpbox is a naked Ubuntu instance. Paste the following block directly into the Bastion terminal to install dependencies, clone your code, and bypass PEP 668 restrictions using a Python virtual environment. (Replace 'YOUR_GITHUB_USERNAME' with your actual username).

    curl -sL https://aka.ms/InstallAzureCLIDeb | sudo bash
    sudo apt-get update
    sudo apt-get install -y docker.io python3-pip python3-venv
    sudo chmod 666 /var/run/docker.sock
    git clone https://github.com/YOUR_GITHUB_USERNAME/viva-dlq-agent.git
    cd viva-dlq-agent
    python3 -m venv .venv
    source .venv/bin/activate
    pip install -r requirements.txt

    MAX_CONCURRENT_QUEUES=5
    ASB_MAX_MESSAGE_COUNT=10
    ASB_MAX_WAIT_TIME=5
    PREFETCH_COUNT=20
    ENABLE_NEW_MESSAGE_ID_ON_RETRY="True"
    IDEMPOTENCY_TTL_SECONDS=86400
    CLASSIFICATION_TTL_SECONDS=600
    MAX_RESUBMIT_COUNT=3
    DUPLICATE_NOISE_THRESHOLD=10
    TELEMETRY_CSV_PATH="reports/telemetry_dashboard.csv"
    IDEMPOTENCY_DB_PATH="data/idempotency.db"
    OLLAMA_MODEL="qwen2.5:0.5b"
    OLLAMA_ENDPOINT="http://localhost:11434/api/generate"

## Phase 4: Agent Hosting Deployment

**Objective:** Deploy the agent to Azure Container Apps.

**Trap Resolution (The Identity Crash):** When mapping User-Assigned Managed Identities into Container Apps, the Python 'DefaultAzureCredential' SDK defaults to looking for a System-Assigned identity, causing a fatal 'ClientAuthenticationError'. To resolve this, our Terraform configuration dynamically queries the exact 'client_id' of the generated identity and explicitly injects it into the container block as 'AZURE_CLIENT_ID'.

**Trap Resolution 2 (The Static Tag Trap):** Terraform will ignore your newly pushed image because the ACR tag remains 'v1.0.0'. To force Azure to pull the new code, append a dummy variable to your LOCAL laptop's '.env' file:

    echo 'FORCE_IMAGE_PULL="001"' >> .env

Return to your **local laptop terminal** and deploy the agent:
```bash
pwsh ./infra/scripts/04-deploy-agent.ps1
```

## Phase 6: Telemetry Extraction & Safe Teardown

**Objective:** Extract the dashboard metrics via Log Analytics and destroy the billing meters whilst protecting the Terraform state.

### 1. Telemetry Extraction
Navigate to your Log Analytics Workspace ('law-dev') in the Azure Portal. Run the following KQL query to extract the telemetry rows broadcasted by the agent, and select 'Export to CSV':

    ContainerAppConsoleLogs_CL
    | where ContainerAppName_s == "ca-viva-dlq-agent-dev"
    | where Log_s startswith "CSV_EXPORT|"
    | extend csv_string = substring(Log_s, 11)
    | extend columns = split(csv_string, ",")
    | project 
        timestamp = columns[0],
        source_queue = columns[1],
        client_id = columns[2],
        message_type = columns[3],
        classification = columns[4],
        pattern = columns[5],
        status = columns[6],
        occurrence_count = columns[7],
        suggested_action = columns[8],
        confidence_score = columns[9]
    | sort by todatetime(timestamp) desc

### 2. Infrastructure Teardown
From your **local laptop terminal**, execute the teardown script to destroy all compute and networking resources. This script deliberately preserves the Storage Account and Key Vault so your remote memory remains intact.

    pwsh ./infra/scripts/99-destroy-all.ps1

**Trap Resolution (The Bastion NSG Catch-22):** 
The teardown script will successfully delete the Virtual Network and compute components, but it will throw a '400 Bad Request' regarding 'nsg-azure-bastion'. This is a known Azure API race condition where Terraform attempts to delete mandatory security rules whilst Azure believes the Bastion subnet is still active.

To resolve this:
1. Go to the Azure Portal and open 'rg-viva-dlq-dev'.
2. Locate the orphaned Network Security Group ('nsg-azure-bastion') and click 'Delete' manually.
3. Run the destroy script one final time to purge the NSG from your local Terraform state cleanly:

```bash
pwsh ./infra/scripts/99-destroy-all.ps1
```
